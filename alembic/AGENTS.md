# alembic DOX

## Purpose

- Postgres schema migrations for the ORM models in `src/db/postgres/models.py`

## Ownership

- `env.py` — wires `target_metadata` to `get_base_metadata()` from `src.db.postgres.init_db`, which imports `models` for its side effect of registering tables
- `versions/<year>/<month>/` — date-nested revision files, named by the `file_template` in `alembic.ini`
- `script.py.mako` — revision template
- `alembic.ini` lives at the repository root and is owned by the root DOX

## Local Contracts

- Migrations run over the sync driver: `alembic.ini` sets `sqlalchemy.url` to `postgresql+psycopg2://octo:octo@localhost:5432/octo`, separate from the asyncpg URL the app uses (`db_settings.POSTGRES_URL`). Point it at the right host before running against anything but a local compose stack
- `recursive_version_locations = true` is required for the date-nested layout; never flatten `versions/`
- Every `models.py` change needs a revision — generate with `uv run alembic revision --autogenerate -m "<slug>"` and apply with `uv run alembic upgrade head`, both from the repository root
- Always read the autogenerated diff before committing: it drops the constraint names SQLAlchemy inferred, so `op.create_foreign_key(None, ...)` and similar need a name filled in
- A new non-nullable column needs a `server_default` in both the model and `op.add_column`, otherwise the migration cannot backfill existing rows

## Verification

- `uv run alembic upgrade head` against the compose Postgres, then `uv run alembic revision --autogenerate` must produce an empty revision if the models and schema agree
